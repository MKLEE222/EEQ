## Why a 24/24 or 8/8 accuracy comparison cannot resolve novelty

On the R2B TUF root-update-only contract B9 can use version-only sufficient
state (24/24). R4-D0 proves that simplification fails with variable
cryptographic old-root authority: version+candidate representation upper
bound 6/8 while a fully source-informed B9 also correctly predicts 8/8.
R2A Kubernetes native updates similarly allow source-aware B9 8/8.
C0 common typed cert envelope 16/16 is reusable software engineering,
not a unique new semantics algorithm; B9 can adopt exactly the same
interface and native verification tools.

Therefore primary new-method contribution cannot be stronger pointwise
decision accuracy against an unrestricted sufficient representation.
It must show an INDEPENDENT downstream quality/efficiency dimension.
The preregistered leading candidate is R4 P3:
  domain-specific semantic adaptation effort when lawful source/authority
  configurations change, at exactly matched native correctness and
  source/actor/claim coverage.

## What must be frozen before any quantitative P3 comparison

1. Prior-art attack over provenance, incremental view maintenance,
   policy verification, certificate reuse, semiring provenance,
   selective prediction and native security protocol verification.
   Neither partition refinement, key verification nor ordinary dependency
   tracking is claimed novel.
2. Exactly two development native families (TUF and Kubernetes), plus
   truly independent semantic-delta groups by family. No old scored R1/R2
   candidates relabeled as newly prospective adaptation cases.
3. Frozen source authority, actor, claim, action/horizon scopes and native
   verifier/version, with ONE independent outcome oracle per family.
4. Two comparable implementation routes:
   - EEQ candidate: reusable typed certificate envelope + source/admissible
     qualification IR, stable generic checker, explicitly counted domain
     semantics adapters and all required maintenance;
   - Strong B9: full native source/qualification/contract access, permitted
     equivalent code reuse, common certificate interface if helpful,
     native library, caching, testing and all reasonable automation.
   Any artificial B9 API/knowledge restriction disqualifies the study.
5. A priori adaptation tasks:
   TUF candidate classes: honest multi-key threshold rotation, adding /
   removing valid old/new signer authorities, stale or missing authorized
   signatures, unavailable qualified root source, non-root-role changes
   irrelevant to root-only decisions.
   Kubernetes candidate classes: multiple concurrently matching bindings,
   namespace-label changes, matchExpressions or parameter qualification,
   policy/binding update events and source-unavailability constraints.
   Only native-supported and immutable cases qualify; unsupported
   features are explicit failures, not silently assumed semantics.
6. Human work measurement must use independent, sufficiently competent
   maintainers, randomized or counterbalanced equivalent tasks and
   blinding to native answer labels until submitted predictions are frozen.
   Measure real engineering wall-clock minutes from task assignment to
   independently native-validated completion, including debugging,
   certificate design/validation, dependency updates and regression work.
   Using only the author's self-measured coding time supports at most a
   descriptive engineering case study, NOT a causal/quantitative P3 claim.
7. Preselected primary metric BEFORE tasks: paired per-change verified
   domain-adaptation effort (minutes) at zero verified unsafe native
   authorizations and at least matched decision coverage.
   Secondary: touched domain semantic code, number of hand-coded
   special-case rules, source acquisition, certificate bytes, verifier
   time, query latency, peak RSS, unknown/refusal rates.
   Code lines changed are secondary and cannot stand for developer time.
8. A fully charged denominator: completed, incomplete, unsupported,
   infra-error, exceeded-budget and setup failures ALL remain visible;
   no replacement or reclassification after native results.
9. Freeze the quantitative success threshold and paired statistical
   reporting plan (sample size, confidence intervals, per-domain
   strata, carryover correction and outlier policy) before any run.
   These are NOT yet specified, so P3 must remain unopened.
10. If B9 matches under fair engineering conditions, choose
    R4_B9_TIE / NO_INDEPENDENT_VALUE, not a substitute metric picked later.

## Separate falsifiable incremental-certificate mechanism candidate

Let pi be a decision-support certificate with exact source IDs, asserted
qualification premises and bound claim/action contract. For a real system
transition a, define Impact(a) as a verified dependency/qualification
change set (not simply changed content hashes).
Potential safe reuse of pi requires checked preservation of ALL
claim-relevant qualification premises and unchanged scoped conclusion,
or a sound adapter-specific invariance certificate.

Two complementary tests are essential:
- SAME SOURCE BYTES, AUTHORITY CHANGED: a source hash alone does not
  prove a credential or policy remains qualified; cache must invalidate
  or explicitly reverify the changed authority dependency.
- DIFFERENT SOURCE EVIDENCE, CONTRACT-IRRELEVANT: when the source changes
  only targets-role qualification but the registered contract is
  TUF root-update-only, a proof-dependency-aware system may avoid
  unrelated decision revalidation while still retaining provenance.

Do not assert a new iff theorem or a new algorithm from these examples.
This is an initial scope for a source-relative certificate reuse
semantics comparison to existing incremental query/dependency systems.
B9 with equivalent verified dependency tracking must remain eligible.
